# korotkiy-url - ДЗ 2 (Kubernetes)

## Какие абстракции Kubernetes использованы

- **ConfigMap `app-config`** - обычные настройки: имя БД, хост и порт БД, порт бэкенда, уровень логов
- **Secret `db-credentials`** - логин и пароль PostgreSQL
- **PersistentVolumeClaim `db-data`** - постоянный диск для данных PostgreSQL, чтобы они не пропадали при пересоздании пода
- **Deployment `db`** - запускает один под с PostgreSQL
- **Service `db`** (ClusterIP) - постоянное имя `db` для базы внутри кластера
- **Job `migrate`** - один раз применяет миграции к базе
- **Deployment `backend`** - запускает поды бэкенда, его можно масштабировать через `kubectl scale`
- **Service `backend`** (ClusterIP) - постоянное имя `backend` и распределение запросов между репликами бэкенда
- **Deployment `frontend`** - запускает поды nginx
- **Service `frontend`** (NodePort) - вход в приложение снаружи кластера

## Как сервисы взаимодействуют между собой

```
Браузер
 |
 v
Service frontend
 |
 v
поды frontend (nginx)
 |
 v
/api/, /s/ -> http://backend:8080
 |
 v
Service backend -> поды backend
 |
 v
db:5432
 |
 v
Service db
 |
 v
PostgreSQL
 |
 v
PVC
```

- Браузер обращается только к фронтенду. Nginx отдаёт страницу, а запросы `/api/` и `/s/` передаёт бэкенду.
- Сервисы находят друг друга по DNS-именам Service (`backend`, `db`). IP-адреса подов меняются при каждом пересоздании, поэтому обращаются не к подам, а к Service.
- Service сам выбирает, какие поды сейчас живы, и распределяет запросы между репликами. Поэтому после `kubectl scale` имя остаётся тем же.
- Job `migrate` подключается к БД через Service `db` и применяет миграции.
- Снаружи доступен только фронтенд, бэкенд и БД видны только внутри кластера.
